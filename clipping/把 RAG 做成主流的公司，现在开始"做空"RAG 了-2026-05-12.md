Pinecone 刚刚几乎等于亲口宣布：RAG 时代结束了。

作为向量数据库赛道的开创者，Pinecone 当年亲手把 RAG 定义成了大语言模型 grounding 的标准范式。过去几年里，大约 80 万开发者、9000 家付费客户，都在 Pinecone 的基础设施上学习如何切 chunk、做 embedding、跑 retrieval。而随着本周一发布面向 Agent 的知识引擎 **Nexus**，Pinecone 现在却开始告诉这些开发者：他们过去学会的那套模式，如今反而成了瓶颈。

## 核心问题：retrieve-read-retrieve 循环

Pinecone 把现有的 retrieval-at-inference 模式形容成「Agent 检索的十条蓝色链接时代」——就像早年搜索引擎只甩给你一堆链接、用户自己拼信息，现在很多 Agent 的 retrieval 本质上也还停留在「AI 版搜索引擎」阶段，不停 retrieve、read、再 retrieve。

**关键数据**：
- 陷在 retrieve-read-retrieve 循环里的 Agent，任务完成率通常只有 **50%–60%**
- Agent **85% 的精力**，其实都消耗在「找上下文」这件事上

把一堆原始 chunk 直接丢给前沿模型，然后期待模型自己理解、自己推理——这套方式既脆弱、又慢，还非常昂贵。而这套描述，其实就是换了个名字的 RAG。

## 新范式：知识编译（Knowledge Compilation）

Pinecone 现在的新关键词叫 **Knowledge Compilation**。核心变化是把「推理」提前了。

整个行业至今都没有一套统一的「知识请求语言」，让 Agent 能清楚表达自己究竟想从知识系统里得到什么——类比：SQL 出现之前，每个应用都得自己实现一套数据访问层；SQL 提供统一接口后，整个应用生态才真正建立起来。

**Agent 目前无法表达的三件事**：
1. 「直接把答案给我，而不是二十段 chunk」——缺乏统一的输出结构约定，token 消耗暴涨
2. 「告诉我答案来自哪个来源，以及它的可信度」——缺乏字段级别的 grounding，输出天然不稳定
3. 「把推理深度控制在标准范围内，并在 500 毫秒内返回」——缺乏统一的 budget envelope，每次调用可能无限下钻

## KnowQL：Agent 知识检索的「SQL」

**KnowQL** 是 Pinecone 为 Agent 设计的声明式知识查询语言，把六个 primitive 封装进一次调用：
- **intent**（意图）
- **filter**（过滤）
- **provenance**（来源）
- **output shape**（输出格式）
- **confidence**（置信度）
- **latency budget**（延迟预算）

**Nexus 的做法**：提前把源数据预编译成带类型、可引用、面向具体任务的知识产物（artifacts）。Agent 查询的不再是原始语料库，而是这些已经整理好的 artifacts——「编译一次，多次复用（compile once, read many times）」。

**Pinecone 声称的效果**：任务完成率提升到 90% 以上，token 开销降低 90%（需生产环境验证）。

## 更大的趋势：「推理」正在向上游移动

不只是 Pinecone 一家：
- **Anthropic Skills**：预编译、可复用的上下文包
- **Cursor Rules**：在编辑器层做同一件事
- **Claude Code subagents**：为不同任务提前打包上下文和工具
- **LangChain context engineering**：Harrison Chase 这几个月一直在强调的方向

Pinecone 只是把这种思路推进到了 retrieval 层。

## 结论

向量搜索会慢慢变成「水电煤」一样的基础设施；Knowledge Compilation 才会成为真正的产品层；而「RAG pipeline」这个词，最后可能会像今天的「LAMP stack」一样，变成一种带着敬意的历史名词。

最可能判断错的，其实也是「时间点」。一个技术范式的衰退，往往都会比厂商宣告它「结束」时来得更慢。但大的方向已经很明显了。
